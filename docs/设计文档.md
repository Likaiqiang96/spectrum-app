# 音频频谱仪 · Android App 设计文档

**版本** 0.3（**两条模式都已经在 App 里实现并在真机验证**：麦克风采样 v0.1、音源 v0.2）
**参考图** B 站视频截图（UP：Given晚椿）——手持式音频频谱显示设备
**目标设备** Meizu M1852 · Flyme 8.1.5.0A · Android 8.1.0 / API 27 / arm64-v8a / SDM710 / 1080×2220 @ 60 Hz / density 480
**构建方式** aapt2 + javac + d8 + zipalign + apksigner（**无 Gradle、无 AndroidX、无第三方库、无 NDK**）

## 0. 结论先行

用户拍板的三件事：**输入模式只有「麦克风」和「音源（当前正在播放）」两种**、**屏下灯带是 VU 电平表**、
**界面只做「设备复刻」**。这两条音频通路**都已经用真机探针验证过**（§4.2）：

| 问题 | 结论 |
|---|---|
| 「音源」（其它 App 正在播的歌）能抓吗？ | **能。** API 27 没有 `AudioPlaybackCapture`，唯一的路是 `Visualizer` 绑 **session 0（全局输出混音）**，实测可用 |
| 需要什么权限？ | **`RECORD_AUDIO` 是必需的**（这台 Flyme 把 P 的要求提前到了 8.1，连绑自己 session 都要；缺了直接 `error: -3`） |
| 系统混音这条路能给什么？ | **每秒最多 20 帧、FFT 最多 1024 点、采样率 44.1 kHz**、8-bit 数据。比麦克风路粗得多 |
| 麦克风能抓吗？ | **能，而且质量更好。** `UNPROCESSED` 源可用，48 kHz，可以跑满 46.9 fps、自研 2048 点 FFT |
| 有什么坑？ | ① 媒体音量 0 / 静音时，混音捕获**全是 0**（App 里已加提示）；② **长音乐可能走 DSP 硬解绕过混音**：本机 `dumpsys media.audio_policy` 确实有 `COMPRESS_OFFLOAD` 输出（output 5/7/8，flags `0x0031`）且 `audio.offload.min.duration.secs=30` → **这一条还没用真实音乐验证**（§13 P1） |

设计因此是**双通路**：麦克风走自研 DSP（高质量），音源走系统 FFT（够用但粗），
两者在渲染层统一成同一套 `SpectrumFrame`。

## 3. 技术选型与取舍

### 3.1 构建：继续用「没有 Gradle」的管线

沿用 `desk-clock-app` / `cloud-album` 的 `aapt2 + javac + d8 + zipalign + apksigner`，
Java + framework only（管线上只有 `javac`，没有 kotlinc，也没有依赖解析）。
本 App 的界面几乎全是自绘（频谱、灯带、菜单、歌词都是 `Canvas`），正好不需要 AndroidX。

**Flyme 安装的坑（已解决，脚本在 `tools/viz-probe/install.sh`）**：这台机器 `adb install` 会返回
`INSTALL_FAILED_USER_RESTRICTED`，系统日志里是

```
W System.err: at com.android.server.hips.intercept.UsbInstallInterception.isStopUsbInstall(...)
W UsbInstallInterception: Stop the application to install through adb!
```

即 Flyme 弹了一个「正在通过USB自动安装以下应用 / 禁止 / 允许」确认框，**17 秒不点「允许」就自动拒绝**。
`install.sh` 的做法是：一边 `adb install`，一边轮询 `uiautomator dump` 的 UI 树，看到「允许」就 `input tap`。

### 3.2 输入模式：两条路，都已在真机跑通

| 模式 | 数据从哪来 | 实测结论 | 质量 |
|---|---|---|---|
| **麦克风** | `AudioRecord`（`UNPROCESSED` → `MIC` 回落）→ **自研 FFT** | ✅ 可用。48 kHz、`UNPROCESSED` 源存在（不受 Fluence 降噪/AGC 污染）、可跑 46.9 fps | **高**（2048 点 FFT，23.4 Hz/bin） |
| **音源（当前正在播放）** | `android.media.audiofx.Visualizer` 绑 **session 0**（全局输出混音） | ✅ **已在 App 里实现并验证**（`core/SystemMixProvider`）。受三条硬约束：**≤20 帧/s、≤1024 点 FFT、44.1 kHz** | **中**（43 Hz/bin） |

「音源」为什么只能走 Visualizer：

| 通路 | 起始 API | 本机 API 27 | 说明 |
|---|---|---|---|
| `AudioPlaybackCapture` + `MediaProjection` | **29** | ❌ 不支持 | 官方正路，换到 Android 10+ 的机器再加，代码里按版本判断即可 |
| `AudioRecord(REMOTE_SUBMIX)` | 19 | ❌ | 需要系统签名权限 `CAPTURE_AUDIO_OUTPUT`，第三方拿不到 |
| **`Visualizer(session 0)`** | 9 | ✅ **实测可用** | 本机唯一可行的路，就是 §3.3 那三条约束 |
| App 内自己解码播放 | 16 | ✅ | **用户明确不要**（要的是"其它 App 正在播的歌"），不做播放器 |

> 探测顺序（进入「音源」模式时）：`AudioPlaybackCapture(29+)` → `Visualizer(0)` → 都不行就提示改用麦克风。
> UI 上要**显示当前真正生效的后端**。

### 3.3 音源模式的硬约束（实测值，不是文档抄的）

| 约束 | 实测值 | 对设计的影响 |
|---|---|---|
| 回调频率 | `getMaxCaptureRate() = 20000 mHz` = **20 Hz**（实测间隔 49.0~51.6 ms） | 分析帧率只有 20 fps → **平滑/插值必须放在渲染线程**（§6.5），不然肉眼能看出卡顿 |
| FFT 点数 | `getCaptureSizeRange() = [128, 1024]` → 取 **1024** | 44.1 kHz 下 **43.07 Hz/bin**：`fMin` 必须提到 **≈90 Hz**；柱数原为 32，**2026-10-17 起与麦克风路一致为 96**（用户反馈「音源模式谱线密度低了一截」）—— 窄于一个 bin 的频带由分带表的几何中心插值补出，不会出现"一根柱子一个 bin"的台阶 |
| 采样率 | 回调参数单位是**毫赫兹**：`44100000` = **44.1 kHz** | 别当成 48 kHz；`BandMapper` 要用实际速率重建 |
| 数据格式 | 波形 = 8-bit **无符号**（静音 = 128）；FFT = 8-bit **有符号**，`real[0],imag[0],real[1],imag[1]…` | 解析见 §6.4 |
| 缩放模式 | `SCALING_MODE_NORMALIZED`（默认）/ `AS_PLAYED` | 用 NORMALIZED，让频谱不受音量旋钮影响（除了下面这条） |
| **音量 0 / 静音** | **数据全 0**（实测两次；音量 6/60 时正常） | 必须有 `SilenceWatchdog` 提示用户（§6.10） |
| 电平 | 全局混音捕获比同音源的轨道级捕获**低约 34 dB** | 自动量程是必需品，不是可选项（§6.7） |

### 3.4 渲染：`SurfaceView` + 专用渲染线程 + `lockHardwareCanvas()`

- 不占 UI 线程，不受 `View.invalidate()` 的 measure/layout/draw 全流程影响；
- `lockHardwareCanvas()`（API 23+）在 Surface 上走硬件加速；一帧只画 ~32 根柱 + 1 条 Path + 14 段灯；
- 用 `Choreographer` 对齐 vsync（在渲染线程的 Looper 上取 `Choreographer.getInstance()`）。

不用 GLES（没有需要 shader 的效果，API 27 也没有 `RenderEffect`），不用 Compose（没有 AndroidX）。

### 3.5 采样与格式

- **麦克风**：48 kHz、单声道、PCM_16BIT（`dumpsys` 显示 `input 0` 只支持 16-bit）、
  `UNPROCESSED` 优先，`minBufferSize = 3840 bytes = 1920 frames`（实测）。
- **音源**：44.1 kHz（系统给）、8-bit 量化、1024 点 FFT —— 分析参数跟着系统走。

### 4.2 真机探针结论（`tools/viz-probe/`，全程媒体音量 0 / 亚低频，没有发出声音）

一个最小 APK（17 KB）在真机上把两条路都跑了一遍。

**① `Visualizer` 需要 `RECORD_AUDIO`（本机把 P 的要求提前了）**

只声明 `MODIFY_AUDIO_SETTINGS` 时，两个 `Visualizer`（session 0 和自建 AudioTrack 的 session）都失败：

```
W ServiceManager: Permission failure: android.permission.RECORD_AUDIO from uid=10111
E               : Request requires android.permission.RECORD_AUDIO
E visualizers-JNI: Visualizer initCheck failed -3
E Visualizer-JAVA: Error code -3 when initializing Visualizer.
→ java.lang.RuntimeException: Cannot initialize Visualizer engine, error: -3
```

`pm grant … RECORD_AUDIO` 之后立刻正常。**结论：RECORD_AUDIO 是音源模式的必需权限**——
这也让权限模型更简单：整个 App 只需要一个运行时权限。

**② session 0（全局混音）确实能抓到数据**

```
A/system-mix(session 0): setEnabled rc=0 enabled=true captureSize=1024 scaling=1
A/own-track(session 585): setEnabled rc=0 enabled=true
A/system-mix wf#1 len=1024 sr=44100000 rms=0.01261
A/own-track  wf#1 len=1024 sr=44100000 rms=0.62679     ← 同一段音源，轨道级比全局高约 34 dB
```

AudioFlinger 里也能看到效果链挂上去了：

```
  2 Effect Chains
    2 effects for session 585        ← 自建 AudioTrack 的 Visualizer
    1 effects for session 0
        - name: Visualizer           ← 全局混音上的 Visualizer（就是我们要的那条）
```

**③ 音量 0 / 静音 → 数据全 0**

同一段音源，`STREAM_MUSIC: Muted=true, speaker=0` 时：波形全 128、FFT 全 0、`getMeasurementPeakRms` 全 0；
把音量设到 6/60 并解除 mute 后数据立刻正常。**这是本机的一个硬行为**，必须在 UI 上兜住（§6.10）。

**④ 麦克风通路（环境噪声，未播放任何声音）**

```
B/microphone: minBufferSize=3840 bytes = 1920 frames
B/microphone: AudioSource=UNPROCESSED OK                      ← 最好的情况：没有降噪/AGC
B/microphone: chunks=372 frames=380928 ffts=37                ← 自研 2048 点 FFT 在真机上跑通
B/microphone 电平: meanRms=0.00228 (-52.8 dBFS)  maxRms=0.02271 (-32.9 dBFS)
B/microphone 分带: 60Hz:-87  386Hz:-100  1561Hz:-98  6307Hz:-104  10045Hz:-104
```

深夜底噪 −52.8 dBFS，60 Hz 附近有 −87 dB 的低频隆隆声，1 kHz 以上都在 −100 dB 以下。
**这条路的动态范围和分辨率都远好于音源路**——夜里安静时也能看到东西，白天更有内容。

### 4.3 离线 DSP 探针（`tools/jvm/`，8 项断言全过）

`bash tools/jvm/run.sh`，不需要设备。只列会影响设计的几条：

| 验证项 | 实测 | 影响 |
|---|---|---|
| FFT 与朴素 DFT 对拍 | 最大误差 4.2e-08 | 自研 FFT 正确（麦克风路直接用） |
| 满幅 bin 中心正弦 | 读数 1.00000 | 归一化系数正确 |
| 非 bin 中心正弦 | 最坏 0.854（−1.37 dB） | 纯音柱高天生有 ±1.4 dB 起伏 |
| 频带映射 | bin 中心**不重不漏**、单音定位 ≥300 Hz 全对、读数 0.86~1.00 与带宽无关 | §6.3 的三条规则是定稿的 |
| 低频定位 | N=2048 @48k 下 200 Hz 以下精度 ±23 Hz（物理极限） | 低频"大山"由窗口宽度决定，不是渲染 bug |
| 平滑器 90% 上升 | τ=15 ms → 3 帧（50 ms）@60 fps | 与 §6.5 一致 |
| FFT 单帧耗时 | 0.069~0.078 ms（host x86_64，预热后） | 推算 SDM710 0.3~1 ms，预算 21.3 ms |

## 5. 数据流水线

```
        ┌──────────────────────────────┐        ┌────────────────────────────────┐
        │ 麦克风路（质量高）            │        │ 音源路（其它 App 的歌）         │
        │ MicProvider                  │        │ SystemMixProvider              │
        │  AudioRecord(UNPROCESSED)    │        │  Visualizer(session 0)         │
        │  48 kHz / 16-bit / hop 1024  │        │  44.1 kHz / 8-bit / max 20 Hz  │
        │  → 自研 窗+FFT(2048)          │        │  → 系统 FFT(1024)，只做解析     │
        └──────────────┬───────────────┘        └───────────────┬────────────────┘
                       │  46.9 fps                              │  20 fps
                       └──────────────┬─────────────────────────┘
                                      ▼
                    SpectrumFrame{ seq, float[] bandDb, bass/mid/treble, vuDb }
                       └── volatile 引用交换（SPSC，双缓冲，零分配）
                                      ▼
        渲染线程（Choreographer 对齐 vsync，60 fps）
          平滑(攻击/释放, 按 dt) → 峰值保持 → 自动量程 → 绘制
          柱形 / 包络线 / 峰值点 / 面积 / 歌词 / 顶栏 / VU 灯带
```

线程模型：

| 线程 | 优先级 | 职责 | 注意 |
|---|---|---|---|
| 采集/分析（麦克风） | `URGENT_AUDIO`（采集）+ `DISPLAY`（FFT） | `AudioRecord.read` + 自研 FFT | 实测 0.07 ms/帧（host），余量巨大 |
| 系统 FFT 回调 | 框架回调线程 | 解析 8-bit 波形/FFT → dB | 回调里**只做解析**，不画不分配 |
| 渲染 | `DISPLAY` + Choreographer | 平滑、峰值、量程、绘制 | 20 fps 输入下的观感全靠这一层 |
| UI | 默认 | 菜单、设置、权限 | 不参与逐帧工作 |

**为什么平滑必须在渲染线程**：音源路只有 20 fps 输入，而屏幕是 60 fps。
在渲染线程按 vsync 的 `dt` 做攻击/释放，视觉才是连续推上去的；放在分析线程会出现 20 次/秒的台阶感。

## 6. 关键算法

### 6.1 分帧与加窗（麦克风路）

滑动窗 2048 点，每次前进 1024（50% 重叠）：

```java
System.arraycopy(win, HOP, win, 0, N - HOP);   // 左移 hop
System.arraycopy(hop, 0, win, N - HOP, HOP);   // 追加新数据
for (int i = 0; i < N; i++) work[i] = win[i] * hann[i];
```

Hann 窗（`w[i] = 0.5 - 0.5·cos(2πi/N)`），相干增益 `WINDOW_GAIN = 0.5`（归一化已实测验证）。

### 6.2 幅度与 dBFS

```
mag[k] = 2·|X[k]| / (N·WINDOW_GAIN)   （DC: 1·|X[0]|/(N·WINDOW_GAIN)）
dbFS   = 20·log10(mag + 1e-9)          ∈ [-∞, 0]
```

实测：bin 中心满幅正弦 = 1.00000；非 bin 中心最坏 0.854（Hann scalloping −1.37 dB）。
显示域统一用 dB——"快落"才自然，峰值衰减才是匀速。

### 6.3 对数频带映射（两条路同一套规则，参数不同）

分带边界：

```
f_k = fMin · (fMax/fMin)^(k/B)
```

取值规则（**三条一起用**，缺一条就会出问题，都是实测出来的）：

1. **bin 中心唯一归属**：bin `b` 属于带 `k` ⟺ `ceil(f_k/binHz) ≤ b < ceil(f_{k+1}/binHz)`；
2. **带内取 max**（不是能量求和）：纯音柱高与带宽无关（实测 0.86~1.00），不会出现 +1.8 dB 漂移；
3. **带内一个 bin 中心都没有时**，在**带的几何中心** `√(f_k·f_{k+1})` 处对幅度谱线性插值
   （取带下沿会把低频峰系统性地推到高频侧——实测过）。

```java
float bandAmp(float[] mag, float f0, float f1, float binHz, int half) {
    int bLo = Math.max(1, (int) Math.ceil(f0 / binHz));
    int bHi = Math.min(half + 1, Math.max(bLo, (int) Math.ceil(f1 / binHz)));
    float m = 0f;
    for (int b = bLo; b < bHi; b++) m = Math.max(m, mag[b]);
    if (m > 0f) return m;
    float fb = (float) Math.sqrt((double) f0 * f1) / binHz;
    int i = Math.max(1, Math.min(half - 1, (int) Math.floor(fb)));
    float t = Math.min(1f, Math.max(0f, fb - i));
    return mag[i] * (1f - t) + mag[i + 1] * t;
}
```

两条路的参数（**必须分开配**）：

| 参数 | 麦克风路 | 音源路 | 理由 |
|---|---|---|---|
| 采样率 | 48000 | 44100（系统给） | — |
| FFT 点数 | 2048（自研） | 1024（系统） | 系统上限 1024 |
| bin 宽度 | 23.4 Hz | **43.07 Hz** | 分辨率差一倍 |
| `fMin` | 60 Hz | **90 Hz** | 音源路低于 2 个 bin 的带没有意义 |
| 柱数 B | 48 | **32** | 音源路 bin 太少，48 根柱会大量共用 bin（视觉上"台阶化"） |
| `fMax` | 16 kHz | 16 kHz | — |
| 分析帧率 | 46.9 fps | 20 fps | — |

高频倾斜补偿（可选，默认开）：音乐/粉噪能量谱约 −3 dB/oct，给每带乘 `min(5.62, (f_center/1kHz)^0.5)`，
（**2026-11-07 起封顶 +15 dB**：原本 16 kHz 处要抬 +24.3 dB，会把 8-bit 量化的 LSB 噪声抬成
"越往高频越高"的假频谱 —— 见 §13 P12 与 `verify/2026-11-07-ui/README-hf-noise.md`）
高频细节才看得见——参考图右端那条粉色尾巴就是这个处理。

### 6.4 系统 FFT 路的解析（8-bit 数据）

```java
// 波形：8-bit 无符号，静音 = 128
double acc = 0;
for (byte b : wf) { double y = (b & 0xFF) - 128; acc += y * y; }
double rms = Math.sqrt(acc / wf.length) / 128.0;

// FFT：8-bit 有符号，real[0],imag[0],real[1],imag[1], …
float binHz = samplingRate / (float) captureSize;   // samplingRate 单位是毫赫兹！
for (int i = 1; i < fft.length / 2; i++) {
    int re = fft[2 * i], im = fft[2 * i + 1];
    float m = (float) Math.sqrt((double) re * re + (double) im * im);   // 0..~181
}
```

- `samplingRate` 回调参数**单位是毫赫兹**（本机 44100000 = 44.1 kHz）——直接拿去除会错 1000 倍；
- 8-bit 量化意味着**动态范围只有 ~48 dB**，弱信号看不到 —— 这正是音源路必须靠自动量程的原因；
- VU 表优先用框架的 `setMeasurementMode(MEASUREMENT_MODE_PEAK_RMS)` + `getMeasurementPeakRms()`
  （单位 **mB**，100 mB = 1 dB），比自己算稳；麦克风路则用自研时域 RMS。

### 6.5 时间平滑（渲染线程，按 dt）

```java
float aUp   = 1f - (float) Math.exp(-dtMs / ATTACK_MS);
float aDown = 1f - (float) Math.exp(-dtMs / RELEASE_MS);
v[k] += (target[k] - v[k]) * (target[k] > v[k] ? aUp : aDown);
```

实测调出来的参数（用户反馈「变化得太慢」后重调，见 `verify/2026-10-15-dynamics/`）：

| | 攻击 | 释放 |
|---|---|---|
| 麦克风路（47 fps 输入） | **8 ms** | **90 ms** |
| 音源路（20 fps 输入） | **22 ms** | **130 ms** |
| VU 表 | 12 ms | 220 ms |

- 系数按 vsync 的 `dt` 算，与帧率无关（换 90 Hz 屏不用改参数）；
- **音源路的攻击要放大到 20 ms 以上**：输入只有 20 fps（50 ms 一帧），攻击太快会看到明显跳变；
- 释放从最早的 250 ms 收到 90/130 ms —— 原来的观感「黏」，这是「变化太慢」的主因。

### 6.6 峰值保持

```java
// 目标高度 = 当前值 + 上升速率 × 灵敏度（上升越快冲得越高）
float rate  = (cur - prev[i]) / dtSec;               // 归一化单位/秒
rise[i]    += (rate - rise[i]) * RISE_SMOOTH;        // 平滑，60 fps 下约 5 帧收敛
float boost = clamp(rise[i] * BOOST_PER_RISE, 0f, MAX_BOOST);
float target = min(1f, cur + boost);

if (target >= peak[i]) { peak[i] = target; hold[i] = HOLD_MS; }   // 菜单可调 0.5/1/2 s，默认 0.5 s
else if ((hold[i] -= dtMs) <= 0) peak[k] = Math.max(v[k], peak[k] - FALL_PER_SEC * dtMs / 1000f);
```

**"被抛出"的两个前提**（缺一个就看不到效果，用户两次反馈后才补齐）：

1. **冲高必须锁存**：速率在瞬态**刚开始**最大，柱子要几十~上百毫秒才涨到顶；若直接把瞬时速率
   加到当前值上（`target = 当前值 + 瞬时冲高`），等柱子涨到顶时冲高已衰减没了 → 峰值点只等于柱高。
   现在升完再保持 **150 ms**，之后按 **300 ms** 时间常数衰减。
1b. **死区必须够大**（用户报"两层峰值"的根因）：麦克风底噪的逐帧抖动换算成 80ms 包络速率约
   **30~55 dB/s**，死区设 20 时几乎每帧都在触发冲高 → 峰值帽永远浮在柱顶上方，
   屏幕上就出现"柱顶一层 + 帽子一层"两条平行轮廓。提到 **70 dB/s** 后：
   真实瞬态（一帧跳 10~40 dB → 110~440 dB/s）照样抛出（实测 `maxRate≈320 dB/s`、
   `maxBoost` 打满 0.45），底噪被挡掉 —— 实测"两层"列占比 **63% → 19%**（剩下的是真实瞬态与下落中的雨点）。
2. **上方必须有空间，但峰值和柱子必须用同一个比例绘制**（这是「两层峰值」真正的病根）：
   早期柱形/面积/包络线画 **86% 高度**（`barSpanH`），峰值点却仍用 **100% 高度**（`spanH`）——
   于是**每个峰值点都被画高了 14%（≈100px）**，而偏移整齐 → 屏幕上就是一条平行于柱顶的第二轮廓线 ✗。
   现在峰值点也用 `barSpanH`；没抛出时与柱子严丝合缝。**峰值是艺术化表现，允许被甩出屏幕**
   （用户明确要求）。

### 6.6.1 弹道模型（重力 + 阻力）

峰值点不再是"瞬时跳变 + 匀速下落"，而是一颗**受重力与阻力的抛射物**（用户要求
「峰值升高和下降可以通过重力模型来模拟，可以通过界面调整重力的大小和阻力」）：

```
瞬态 → 初速度 v0 = sqrt(2·g·h)    // 仅当峰值点**已落回柱子**时生效（grounded 判据）
每帧 → v -= g·dt;  v *= (1 - drag·dt);  pos += v·dt
落地 → pos < 柱高 时 pos = 柱高, v = 0
```

⚠️ **grounded 判据不能省**：早期写法任何瞬态都会重置初速度，于是峰值点**还没落地就在半空中被重新蹬起**
（用户报的 bug）。现在只有贴地（`pos ≤ 柱高 + ε` 且 `v ≤ 0`）才允许再次发射。

- **重力**（菜单「重力」）：0.2g / 0.5g / 1g / 2g / 4g，基准 3.0 归一化高度/秒²；
- **阻力**（菜单「阻力」）：无 / 低 / 中 / 高（0 / 0.6 / 1.6 / 4.0 每秒）；
- 「峰值」菜单的保持时长变成**到顶后的悬停时间**（默认 0s = 纯弹道）。

实测（假频谱瞬态、假设备 90fps）：初速度 **1.81 归一化/秒**，随后按重力平滑衰减
（1.81→1.77→1.63→1.50→1.38→1.25→1.13→1.01），峰值点最高飞到柱子上方 **1.276 屏高（≈755px）**
—— 早已飞出屏幕，由屏幕自然裁掉。
   另外「抛出量」与「峰值保持」拆开：抛出部分按 120 ms 时间常数快速衰减（短促一脚），
   峰值保持只跟着柱子走（保持期满按设定速度下落），两者相加才是显示值。

实测（假频谱 150 ms 方波瞬态，频谱高 717px）：柱子到达最高点那一帧，峰值点高出
**101 / 473 / 225 / 253 px**，全程最大 **700 px**（四个频带）—— 几乎从底部甩到顶部，
随后按 1.6 屏/秒匀速下落。（灵敏度 `BOOST_PER_DB_RATE = 0.0022`、上限 `MAX_BOOST = 0.45`、
死区 20 dB/s；用户反馈"抛得不够高"后从 0.0009/0.32 提上来。）

**峰值点形状（用户反馈「同一个频率出现两个点」后修正）**：

| 样式 | 形状 | 防重复措施 |
|---|---|---|
| 柱形 / 密线 / 疏线 | 与谱线等宽的小矩形帽 | **只在峰确实抛离柱顶（> 1.1×帽高）时才画**，否则帽与柱顶重合会被看成两个点 |
| 波形 | 小方块，**每带 3 个**（相邻带插值），边长 `bandW*0.16` | 早先每带 2 个大点（12.6px 宽 / 21px 间隔）会被看成"一个频率两个点" |
| 三角 / 面积 / 实心 | 小方块 | — |

**冲高与变化速度挂钩**（用户要求：「频谱变化的速度越快，峰值点应该上升得越高」）：
峰值点不是贴在柱顶，而是按**该频带当前的上升速率**额外抬高
（`BOOST_PER_RISE = 0.016` 秒、上限 `MAX_BOOST = 0.32` 屏高）。
慢变化几乎贴着柱子；鼓点/镲片这种瞬态会把点"甩"到柱子上方，然后再按上面的规则匀速落下来（雨滴）。
实测同一个假信号源下，不同频带/不同瞬态的冲高分别是 **62 / 79 / 157 / 198 px**（满高 207 px），
即冲高确实随变化速度连续变化，而不是每次都顶到天花板。

**「雨滴」效果**（用户要求）：一有更高的柱子就瞬时顶上去 → 短暂悬停 → 然后**匀速下落**
（`FALL_PER_SEC = 1.6`，即满量程 0.6 秒落完），落到柱子高度就贴合。
早期用的是「保持后按 20 %/s 指数衰减」，观感是「停住不动慢慢缩」，不是雨滴。

实测（每帧 20 ms）：攻击 80 ms 冲到顶 → 悬停 540 ms → 以 ≈250 px/s 匀速下落（满高 207 px，≈0.8 s 落满）
→ 下一个瞬态再次冲顶。下落轨迹见 `verify/2026-10-15-dynamics/01-peak-rain.png`，
"冲高 + 下落"的完整轨迹见 `verify/2026-10-15-dynamics/03-kick-overshoot.png`。
峰值点画成柱顶的青色小方块（`Theme.PEAK_DOT`，不能用纯白，见 P11）。

### 6.7 量程与自动增益（菜单「范围」）

实测依据：全局混音捕获比轨道级低 **~34 dB**，不同机器/不同歌曲差得更多；8-bit 量化动态范围被压缩。
所以**自动量程是必需品**：

| 档位 | 行为 |
|---|---|
| **自动（默认）** | **P95 → 显示高度 0.72，P10 → 0**，显示窗口 = `clamp(P95−P10, 22, 60) dB`；P95 按 ±10 dB/s 限速平移（锚点由 0.9 降为 0.72 是为了给峰值点留"被抛出"的空间，见 §6.6）|
| −60 / −80 / −100 dBFS | 手动固定地板（上限 0 dBFS） |

P95/P10 用 **64 桶直方图**近似（每帧 32~48 次累加 + 每 8 帧衰减一次），不排序、不分配。

**窗口为什么跟着信号分布走**：早期版本用"P95 下面固定 32 dB"，结果在**窄动态范围**信号
（8-bit 量化、压缩得很厉害的流行歌、或测试用的白噪型信号）下，所有频带都挤在 P95 附近 3~4 dB 内，
整屏贴顶 —— 用户实测反馈的"每个频段都接近饱和"就是这个。

**这一节踩过的三个坑**（都已修，见 `verify/2026-10-15-autorange-fix/`）：

1. **限速必须按"距上次更新的真实时长"算**。直方图是每 8 帧才结算一次，
   如果限速写成 `6 dB/s × 单帧 dt`，实际速率会慢 8 倍（实测慢了约 25 倍），
   P95 永远追不上电平 → `floor` 偏低 → 整屏贴顶。
2. **窗口要自适应**（见上表），不要写死。
3. **任何"电平补偿"都不要加到频带值上**。音源路的 +30 dB 补偿曾经加在频带值上，
   而直方图的 dB 夹在 `[−100, 0]`，于是响的频带全堆在 0 dB 那一格、P95 被顶到天花板。
   现在补偿只加在 **VU 表的 RMS**（绝对刻度需要），频带值保持原始 dB 交给自动量程做相对映射。

调试面板会显示 `floor / p95 / span / p10`，量程行为可以直接肉眼核对。

### 6.8 低音 / 中音 / 高音

`bass = 60~250 Hz`、`mid = 250 Hz~4 kHz`、`treble = 4~16 kHz` 三段能量（dB），
用于参考图左侧的数字读数、节拍检测和低音指示条（A6）。灯带**不用**它（灯带是 VU 表）。

float norm = Math.max(0f, Math.min(1f, (db - FLOOR_DB) / (0f - FLOOR_DB)));   // FLOOR_DB = -45

### 6.10 音量 0 的兜底（本机实测的坑）

音源路在媒体音量 0 / 静音时拿到的是**全 0**，跟"没在放歌"长得一模一样。所以要有 `SilenceWatchdog`：

- 连续 **3 秒**（60 帧）所有频带都低于地板且 VU 恒为 0 → 判定为"疑似静音"；
- 屏上给一行小字：**「媒体音量为 0，请调大音量」**（麦克风路不提示，因为麦克风不受影响）；
- 一旦有数据就撤销；同一状态只提示一次，别刷屏。

### 4.x 第二台验证机（2026-10-17）

| | 小米 10 (umi) | 魅族 M1852 |
|---|---|---|
| 系统 | **Android 13 / API 33** | Android 8.1 / API 27 |
| 屏幕 | 1080×2340 @ **90Hz** / 440dpi | 1080×2220 @ 60Hz / 480dpi |

**结论：两条音频通路都能跑** —— 麦克风路 ✅；**音源路（`Visualizer` session 0 全局混音）在 Android 13 上也可用** ✅
（AOSP 对 session 0 要求 `CAPTURE_AUDIO_OUTPUT` 签名级权限，原本担心 13 会拒；实测 MIUI 放行，只要 RECORD_AUDIO）。
帧率 **90fps**（跟随 90Hz vsync —— 渲染循环本就按 dt 积分，与刷新率无关，一行没改），渲染耗时 0.7~1.3 ms。

**踩到的坑**：为 Android 11+ 加的 `setDecorFitsSystemWindows(false)` + `getInsetsController()`，
在 `onCreate`（`setContentView` 之前）调用时 `mDecor` 为 null → **启动即崩**（魅族 API 27 走不到这段，所以没暴露）。
修法是先取 `getDecorView()` 再取 controller，并整段 `try/catch` 打日志降级。

### 7.3 配色（菜单「颜色」）

按**横向位置**（频率）取色，一条 `LinearGradient` 覆盖频谱区：

| 位置 | 0.00 | 0.25 | 0.50 | 0.75 | 1.00 |
|---|---|---|---|---|---|
| 色标 | `#00E5FF` 青 | `#2E6BFF` 蓝 | `#8A5CFF` 紫 | `#E040C0` 品红 | `#FF3B30` 红 |

预置 4 套：**青红渐变（默认，对齐参考图）** / 绿黄红 / 纯白 / 自定义 RGB。
面积填充用同一条渐变的 0.85 透明度，柱形不透明，包络线 = 70% 白 + 30% 本柱色，峰值点纯白，
**颜色菜单（2026-10-17 扩充）**：
青红（默认）/ 绿黄红 / 纯白 / **流光溢彩** / 单色红 / 单色绿 / 单色蓝 / 单色紫。

- 单色档：`barPaint` 去掉 shader、直接给纯色；
- **流光溢彩**（用户要求「从低频到高频颜色按彩虹色缓慢滚动」）：铺一条**一个周期（= 频谱宽度）**、
  `TileMode.REPEAT` 的 `LinearGradient`，每帧只更新一个复用的 `Matrix` 做平移
  （`setLocalMatrix`）——**零分配**；
  色相取 **S=0.88 / V=1.0**（略降饱和提亮，比纯饱和更「溢彩」）；速度 **420 px/s**（约 4.6 秒一圈；
  一开始设 85 px/s（22 秒一圈），用户反馈「并没有流动起来」——平滑彩虹缺少可追踪的特征，
  太慢就等于静态。现为 **320 px/s ≈ 6 秒一圈**。平移取正号 → 色带由低频向高频（左→右）流动；
- **流光**：另有一道 22% 宽、7 秒扫一遍的柔光带。实现上**不是**用 `clipPath` 裁剪（硬件层上复杂路径
  裁剪实测把渲染从 5.5 ms 拉到 **16.1 ms / 49 fps**），而是**对每根柱子按它到光带的相对位置算
  alpha**（`sin(πu)` 剖面）再叠一层白色圆角矩形 → **5.5 ms / 60 fps**，零分配、零裁剪。
- ⚠️ **踩过的大坑（用户报「低频不会出现绿/蓝/紫」）**：第一版铺的是「两倍宽度 + 两圈色相 + CLAMP」。
  平移后窗口左侧的采样点会落到渐变范围**之外**，被 CLAMP 夹成第一个色标 —— 于是**低频端被钉死在红色**，
  只有中高频在动。改成「一圈宽度 + `REPEAT`」后，任意平移都无缝，低频端会完整循环所有颜色。
  实测低频端 x=250 的色相随时间：77° → 308° → 177° → 47° → 274°（黄绿→品红→青→橙红→紫）。
- 实测：单帧内色相斜率 **0.188 °/px = 正好一个完整彩虹铺满频谱宽度**（1915 px）；
  色相在固定点以约 45~60 °/s 变化（≈6 秒一圈）。
- 逐帧追踪「红色带」中心 x：618 → 625 → 634 → 642 → 650 px，**稳定向右**（低频→高频）。

> 颜色**不随电平变化**——参考图里"低频大山是青色、高频平尾是红色"证明色相只跟频率有关。

## 8. UI 与交互

### 8.1 交互

- **顶栏菜单 4 秒无触摸自动隐藏**（用户要求），点屏幕任意处再出现；子菜单 3 秒无操作自动收起。
- 左右手势区各**内缩 8%**（8%~32% 调亮度、68%~92% 调增益）：贴边滑动会同时被系统边缘手势
  （Flyme 侧边返回）吃掉，App 收到事件的同时 Activity 被送回后台 —— 实测踩过这个坑。
- 歌词区原来画了一条「——」占位（参考图里无歌词时的那一横）；歌词功能尚未实现，占位会让人
  以为屏幕坏了，**已删除**，等真做歌词时再按 LRC 时间轴画当前行。
- 顶栏菜单项 → 展开子项浮层（红底高亮当前值，同参考图）。
- **左侧 25% 区域上下滑动 = 屏幕亮度**（`WindowManager.LayoutParams.screenBrightness`，只影响本 App，
  不需要系统权限）；**右侧 25% 区域上下滑动 = 增益**（±24 dB，抬手才落盘）；滑动时屏上给提示条。
- ⚠️ **踩过的坑**：滑动量必须**在当前值上累加本帧增量**。早期写成 `起始值 + 本帧增量`，
  每次 MOVE 都在同一个基准上覆盖 → 只有最后几像素生效，用户反馈「非常不灵敏」。
  另外拖动时**不要**每帧写 SharedPreferences（会卡），改成 `setGainDb()` 只改内存、
  抬手 `persistGain()` 落盘。实测：200 px 滑动 = 增益 +12.8 dB、亮度 +28%（修复前几乎不动）。
- 菜单行那一条、以及子菜单展开时，触摸**优先给菜单**（否则滑动区会把菜单项盖住）。
- 左右滑动频谱区 → 调整 fMax；长按 → 显示当前生效的音频后端、fps、分析耗时。
- 音量键 → 「范围」快捷调整（不改系统音量）。
- 返回键：先收浮层，再退出。
- 沉浸全屏（隐藏状态栏/导航栏），`FLAG_KEEP_SCREEN_ON`。

## 11. 性能预算与验证方案

### 11.1 每帧预算

| 路径 | 阶段 | 预算 | 依据 |
|---|---|---|---|
| 麦克风 | 采集 + 转 float | < 1 ms / 21.3 ms | `minBufferSize` 实测 1920 帧 |
| 麦克风 | 加窗 + FFT(2048) | **≈0.07 ms（host）→ 推算 SDM710 0.3~1 ms** | 离线探针实测 |
| 麦克风 | 分带 + dB | < 0.3 ms / 21.3 ms | — |
| 音源 | 解析 1024 点 8-bit + 96 带 | **< 0.2 ms**（不用做 FFT，只做 512 点幅度 + 分带） | 典型 3.2 ms / 60 fps；96 根柱子全部顶满的极端画面 11.8 ms / 51 fps |
| 渲染 | 平滑 + 峰值 + 绘制 | < 4 ms / 16.7 ms | 144 柱 + 1 Path + 40 段灯（实测 1.4 ms @90fps）|

启动时预热（跑 200 次空 FFT）避免首帧 JIT 抖动；渲染循环里不 `new`（`Paint`/`Path`/`LinearGradient`
只在设置变化时重建，路径用 `reset()` 复用）。

### 11.2 桌面 JVM 逻辑测试（不需要设备）

`bash tools/jvm/run.sh`（已跑通 8 项）：FFT 对拍、幅度归一化、Hann scalloping、频带映射不重不漏、
单音定位、单音读数一致性、平滑器时间常数、FFT 单帧耗时。

## 13. 风险

| # | 风险 | 影响 | 对策 |
|---|---|---|---|
| **P1** | **长音乐走 DSP 硬解（offload）绕过混音，`Visualizer` 抓不到**。本机证据：`dumpsys media.audio_policy` 里 output 5/7/8 的 flags = `0x0031 (DIRECT\|COMPRESS_OFFLOAD\|NON_BLOCKING)`，且 `audio.offload.media=true` / `audio.offload.min.duration.secs=30` | 音源模式对"正常听一首歌"可能失效（短音频/非压缩格式不受影响） | 用 `/sdcard/Music/probe_silent.mp3`（75 s，只含 40/70 Hz，喇叭发不出来）在音量 index 4 下放一遍即可判定（§11.3）；真不行就让用户改用麦克风模式，UI 明确说明并一键切换；换 29+ 的机器用 `AudioPlaybackCapture` 没这个问题 |
| P2 | 系统混音捕获比轨道级低 ~34 dB，且 8-bit 只有 48 dB 动态 | 安静段落看不到东西 | P95 自动量程（§6.7）+ 渲染层平滑；必要时把地板抬到 −45 dB |
| P3 | 媒体音量为 0 时数据全 0（实测） | 用户以为 App 坏了 | `SilenceWatchdog` 明确提示（§6.10） |
| P4 | 音源路只有 **20 fps / 1024 点**，8-bit 量化底噪较高（实测：给一个很响的亚低频测试音时，整屏柱子会被泄漏/量化底噪顶满；真实音乐待观察） | 视觉比麦克风路"慢半拍"、低频更糊 | 平滑/插值放渲染线程；`fMin=90 Hz`；柱数已从 32 提到 96（与麦克风一致），低频段靠几何中心插值补细节 |
| P5 | 麦克风被其它 App 抢占（`ERROR_DEAD_OBJECT`） | 频谱卡死 | 检测错误码 → 停 200 ms → 重建 `AudioRecord`，统计重建次数 |
| P6 | 歌词依赖"通知使用权" | 用户不开就没有歌词 | 做成可选功能；没权限时显示「——」，不弹窗骚扰 |
| P7 | 「三角」样式几何未确认 | 可能与实物不像 | 先按字面实现，预留可替换的绘制函数；需要用户提供另一帧截图 |
| P8 | 首帧 JIT + `Paint` 构造造成启动卡顿 | 前 1 s 掉帧 | 启动预热 200 次 FFT；`Paint`/`Path` 提前构造 |
| P9 | Flyme 安装弹窗超时（17 s）导致 `INSTALL_FAILED_USER_RESTRICTED` | 升级装不上 | `tools/viz-probe/install.sh` 自动点「允许」；文档写清 |
| P10 | 低频定位精度受窗口限制（麦克风路 ±23 Hz，音源路 ±43 Hz） | 有人觉得"低频柱子在乱跳" | 文档写清这是分辨率而不是 bug；麦克风路可用更大 N（4096/8192）换精度 |
| P12 | 音源路 8-bit 量化 + 倾斜补偿 → 高增益下高频底噪被抬成假谱（用户反馈「没声音但高频很高、越高越亮」）| 高增益时屏幕出现一片假的上升斜坡 | 倾斜补偿封顶 +15 dB；音源路加 −42 dBFS 底噪门限（低于门限直接清零频带）|
| P11 | Flyme 夜间模式会把**实心浅色块**改写成深色（文字 / 细线 / 饱和色不受影响） | 白色机身、白色峰值点都被吃掉过 | 机身直接用深色、峰值点用饱和亮青 `Theme.PEAK_DOT`，不依赖系统改写 |
